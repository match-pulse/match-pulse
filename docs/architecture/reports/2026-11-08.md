This report describes the current architecture of MatchPulse. It is a dated
snapshot, not a final submission. It links to the detailed records rather than
duplicating them. The authoritative statements remain the linked records; where
this report and a record disagree, the record wins.

## 1. Executive summary

MatchPulse is a football tournament platform for local competitions. Spectators
buy tickets, register for a place, follow live match data and trade prediction
points on the match outcome. Points are redeemable for future ticket discounts,
and aggregated prediction data is sold to clubs.

The system is a **single Next.js application and a single PostgreSQL database**.
Critical business rules are enforced inside PostgreSQL transactions and
row-level security, not in the browser or in ad hoc application checks. The
architecture is best described as a **modular monolith at the domain and database
boundary**, with a layered Next.js delivery shell: one deployable, one database,
explicit domain modules in the schema and RPC surface, and executable guards on
the application imports.

The selected architecture characteristics are **Reliability, Elasticity,
Deployability, Testability and Security**. Reliability and Security are measured
for the recorded mechanisms; Elasticity is partially measured; Deployability is
measured for local/CI; Testability is measured with one stated injection gap. No
production availability, production latency or real-user claim is made.

## 2. Kata

The current kata is [`../kata.md`](../kata.md). It has the four parts the course
requires and numbers the requirements K1–K15 so the characteristics can refer to
them.

### 2.1 Description

A platform for managing local football tournaments. Spectators buy tickets,
register for a place, follow live match data and trade prediction points on the
match outcome. Points are redeemable for ticket discounts. Aggregated,
time-stamped prediction data is sold to clubs.

### 2.2 Users and scale

| User | Expected number and pattern | What they do |
| :--- | :--- | :--- |
| Spectators | Hundreds concurrently during a match; thousands across a tournament. A planning assumption, not yet measured. | Buy tickets, register, follow the match, trade, redeem rewards. |
| Tournament staff | Roughly 1–5 per tournament, active at setup, during the match and at result time. | Create matches, set capacity, update scores, finalise results. |
| Club representatives | A few analysts per club, reading/exporting after matches. | Access and export aggregated prediction data. |

Venue capacity bounds participation; the platform must not register more places
than the venue allows.

### 2.3 Requirements

| ID | Requirement |
| :--- | :--- |
| K1 | Staff create and manage matches and ticket sales. |
| K2 | Staff set a maximum participant capacity per tournament, bounded by the venue. |
| K3 | Spectators buy tickets and receive prediction points. |
| K4 | Spectators register while capacity remains and are told when the tournament is full. |
| K5 | Spectators view the live scoreboard, timer and available market on their phones. |
| K6 | Spectators trade points on HOME/DRAW/AWAY while the match is running, entering and exiting at current odds. |
| K7 | A spectator chooses the points to commit; the market prices the position, and the spectator may exit part or all before the result is finalised. |
| K8 | Exiting settles against current odds: a gain when the implied probability rises, a proportional loss when it falls. |
| K9 | The platform takes no commission on entries, exits or settlement. |
| K10 | Re-entry after closing a position is delayed by an escalating cooldown; exits are never blocked or charged. |
| K11 | Match scores are updated during the game, and staff finalise the result. |
| K12 | Finalisation settles open positions: winning shares pay one point each, losing shares pay nothing. |
| K13 | Spectators redeem points for future ticket discounts. |
| K14 | Club representatives access and export aggregated prediction data, including how the crowd's view changed. |
| K15 | The platform sells aggregated prediction data; points cannot be converted to cash. |

### 2.4 Additional context

- Traffic peaks during matches, with hundreds of concurrent spectators as the
  current planning assumption.
- Participation must never exceed capacity, including simultaneous requests.
- Balances, positions and trade records must remain consistent under concurrency.
- The data is valuable because it combines the crowd's aggregate position with
  time.
- Revenue comes from club data sales; points are not cash.
- The first implementable increment covers capacity-safe registration and the
  live market. Ticket purchase, rewards redemption and club analytics are part of
  the product vision but are not all implemented.

## 3. Architecture characteristics

The full derivation, course-vocabulary mapping and SMART table are in

### 3.1 Selection

| **Reliability** | K2, K4, K6–K8, K10–K12 | Capacity, balances, positions and settlement are concurrency rules; failure corrupts the ledger. | 100 concurrent registrations, capacity 32: 32 accepted, 68 refused, 0 transport errors; no negative balance; one-shot resolution; idempotent retries. | Measured for recorded mechanisms; FND-002 open. |

### 3.2 Course-vocabulary note

The course's consolidated table lists 12 characteristics. It does not list
Reliability or Security. The same course discusses Reliability as an operational
characteristic and uses Security as the example of an implicit characteristic.
This report names them explicitly rather than forcing the domain risk into
Fault tolerance or leaving security implicit:

- **Reliability** is the correct name for "the system functions correctly under
  specified conditions for a specified period." The conditions here are
  simultaneous requests; the period is the burst.
- **Security** is an implicit cross-cutting characteristic made explicit. The kata
  does not use the word, but the staff boundary, the points ledger and club
  privacy require it.

### 3.3 What is not selected

Performance is not selected separately; the only time target is the burst p95
under Elasticity. Scalability is not selected because the kata states peaks, not
growth beyond one deployment. Fault tolerance is not selected because there is no
hardware-failure target. Modularity, maintainability, evolvability, simplicity,
overall cost and partitioning type are design considerations, not primary
success drivers for the first increment. The full rationale is in the
characteristics document.

## 4. Architecture style and module boundaries

### 4.1 Style

MatchPulse is a **modular monolith** in the sense that matters here:

- one deployable Next.js application;
- one PostgreSQL database;
- explicit domain modules in the schema and RPC surface;
- no network boundary between modules;
- no separate deployment or independent scaling claim.

It is **not** a textbook code-level modular monolith with a `modules/` directory
per domain. The Next.js layer is organised by technical role: routes and Server
Actions, client components, and shared server utilities. The domain boundaries
are enforced primarily in PostgreSQL and by the architecture guard. This
distinction is stated explicitly so the label is not overclaimed.

### 4.2 Domain modules

| Module | Tables / functions | Responsibility |
| :--- | :--- | :--- |
| Identity and access | `profiles`, auth trigger, RLS policies, grants | Supabase Auth identity, roles, row-level access |
| Tournaments | `tournaments`, `registrations`, `register_for_tournament` | Capacity-bounded registration and uniqueness |
| Markets | `markets`, `market_positions`, `market_trades`, `market_entry_cooldowns`, `market_payouts`, `open_trade`, `close_trade`, `resolve_market`, `market_public_trades` | LMSR pricing, entry/exit, cooldown, one-shot resolution |
| Trade requests | `trade_requests`, request-key logic in the trade RPCs | Idempotent retries and payload mismatch refusal |
| Delivery and operations | `/api/health`, `src/lib/logger.ts`, `bun run smoke`, operations runbook | Health, logs, delivery and recovery evidence |

### 4.3 Dependency rules

- Client components call Server Actions; they do not import the server Supabase
  client.
- Server Actions validate input and call authorized RPCs; they do not mutate
  tables directly.
- Mutation RPCs are `SECURITY DEFINER`, resolve `auth.uid()`, fix
  `search_path`, and grant execute only to `authenticated`.
- Direct table writes are revoked; RLS restricts private reads to the owner.
- The service-role key is a local test/administration credential, never an
  application runtime key.

`scripts/check-architecture.ts` enforces the text-level rules: no service-role
key in `src/`, no direct table mutations, no server-client imports from
components, no retired client import, and RPC definitions with auth checks and
explicit grants. This is a guard, not a proof; the database-backed authorization
suite is the behavioral check.

### 4.4 Why not microservices

The domain has one bounded context, one database and one developer. Splitting it
would add network failure modes, distributed consistency and operational work
without a requirement that justifies them. The modular monolith gives explicit
boundaries and database-enforced invariants at a fraction of that cost. If club
analytics becomes a separate workload with its own scaling driver, extraction can
be reconsidered; that is a future condition, not a current property.

## 5. System overview

### 5.1 Runtime view

1. A browser requests a page from the Next.js App Router.
2. The page resolves the current Supabase Auth session from cookies.
3. Server-rendered data is read through the cookie-based Supabase client; RLS
   limits private rows to the authenticated user.
4. A mutation is submitted to a Server Action.
5. The action validates the form shape and calls an authorized PostgreSQL RPC.
6. The RPC resolves the caller with `auth.uid()`, locks the relevant rows,
   enforces the business rule and commits the trade, position, balance and
   request-key state atomically.
7. The page refreshes and renders the new state.

### 5.2 Data flow for a trade

`MarketTrader` → `enterPosition` or `exitPosition` → `open_trade` or
`close_trade` → market/profile/cooldown/position rows → `market_trades` and
`trade_requests`. The client supplies one request key across retries; the
database claims the key before the trade, replays a completed request, refuses a
different payload, and commits the request and trade together.

### 5.3 Security boundary

Supabase Auth establishes identity. `profiles.role` distinguishes fans and
organizers. RLS and grants restrict reads and writes. The mutation RPCs are the
only write path. `resolve_market` additionally requires the organizer role. The
public trade feed exposes recent trades without identity.

## 6. Domain model and invariants

The domain entities are matches, tournaments, registrations, profiles, markets,
positions, trades, payouts and trade requests. The critical invariants are:

- INV-01: registrations never exceed `max_capacity`, including under concurrent
  requests.
- INV-02: a user cannot hold two registrations for the same tournament.
- M-INV1–M-INV8: market window, budget-bounded entry, ceil debit, floor credit,
  no negative balance, no oversell, one-shot resolution, no commission.
- M-INV9: a retried entry or exit with the same request key replays the recorded
  trade and does not duplicate a debit, credit, position or trade.
- INV-05 / A-INV1–A-INV5: authentication, RLS, least privilege and
  organizer-only resolution.

The authoritative status is the
[invariant registry](../../methodology/checkpoint-A/02-invariants.md). The key
distinction is between **enforced** (the database has a mechanism) and
**verified** (the mechanism was observed failing when deliberately weakened).
Five market invariants and the M-INV7 detail set remain enforced but not
fault-injected (FND-002).

## 8. Decisions and alternatives

| Decision | Reason | Record |
| :--- | :--- | :--- |
| Next.js + Supabase + managed Postgres | One developer, two deadlines; database-enforced invariants; no infrastructure work | [ADR-001](../adr/001-use-nextjs-and-supabase.md) |
| Live LMSR market with atomic entry/exit and one-shot resolution | The domain needs immediate, unambiguous point movement; eventual consistency would be wrong | [ADR-002](../adr/002-live-prediction-market.md) |
| Authentication, RLS, grants and `SECURITY DEFINER` RPCs | Direct table writes would bypass the business rules; the UI is not the authorization boundary | [ADR-003](../adr/003-authorization-rls.md) |
| Request-key idempotency | A retry must not charge or pay twice; the cooldown is not a request key | [Idempotency change](../../methodology/checkpoint-D/03-change-scenario-idempotency.md) |

Rejected alternatives include a Spring Boot stack (not justified by the domain),
self-hosted PostgreSQL (operational work without a measured driver), event-driven
prediction processing (eventual consistency where the answer must be immediate),
microservices (distributed cost without a driver) and event sourcing (extra
operational surface without a requirement).

## 10. Trade-offs and residual risk

The main trade-offs are Reliability vs Elasticity (pessimistic locking protects
the invariant at the cost of peak throughput), Testability vs time to market
(strong tests only for domain invariants), Deployability vs control (managed
platform vs vendor coupling), and Security vs simplicity (a small RPC surface
with a high-trust boundary).

Residual risks are recorded in the
[findings register](../../methodology/findings-register.md) and the
[residual risk register](../../methodology/checkpoint-C/05-residual-risk.md):
FND-002 (remaining fault injections), FND-004 (p95 observed but not a hard gate),
FND-006 (no hosted deployment or production recovery), FND-007 (no real organizer
evidence), FND-008 (no independent review). FND-003 (idempotency) is fixed.

## 12. Reproducibility

1. Start the local Supabase stack and replay migrations: `supabase start`,
   `supabase db reset`.
2. Write the local credentials to `.env.local`.
3. Run `bun install`, `bun run build`, `bun run test`, `bun run lint`,
   `bun run typecheck`, `bun run check:architecture`.
4. Start the app with `bun run start` and run `bun run smoke`.
5. Follow the [operations runbook](../../operations/runbook.md) for release,
   rollback and recovery.

The detailed setup is in [`../../../README.md`](../../../README.md).

## 13. Limitations

- No hosted deployment, production TLS/DNS, external monitoring or alerting.
- No production backup/retention/RTO/RPO; the recovery drill covers the
  application-owned `public` schema only.
- No real organizer or fan observation; the problem claim is still a hypothesis.
- No independent human review.
- Five market invariants and the M-INV7 detail set remain without observed-red
  fault injection.
- The kata's user numbers are planning assumptions.
- The system is not a complete product: ticket purchase, rewards redemption and
  club analytics are described but not all implemented.
