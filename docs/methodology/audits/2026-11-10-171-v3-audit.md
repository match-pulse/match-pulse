## Summary

This is the first formal software audit in the repository. There is no prior audit report and no prior audit finding in the register. The audit is **static**: this environment has no Bun, Node, Docker or local Supabase, so no lint, typecheck, build, database test, CLI test or browser test was re-executed. Evidence comes from the implementation, migrations, tests, CI configuration and recorded verification records.

The system is coherent for a course prototype, and the database-first authorization design is visible in the migrations. The audit nevertheless found **20 findings: 3 Critical, 9 Major, 6 Minor and 2 Informational**.

The most consequential findings are:

1. **Anonymous sign-ins are still enabled** in `supabase/config.toml`, although ADR-009 and the current documentation say anonymous sessions were removed. Every anonymous auth user receives a profile with 200 points and can use every RPC granted to the authenticated role, including club creation and trading. This is a direct identity and points-economy bypass.
2. **A former staff member or event creator retains direct read access to attendee identity** through the legacy `tickets_select_organizer` RLS policy. Removing the member from the club does not revoke it.
3. **The prediction-market lifecycle is not tied to the match result.** Entries remain open after a match is `FINISHED` and its score is public, and a club can resolve the market at any time with an arbitrary winner. This permits post-result arbitrage and points creation.

Several claims marked **Verified** in the invariant registry are not supported by the tests found in the repository. The individual findings below identify the specific gaps; AUD-012 records the evidence-quality issue itself.

## Finding Details

### AUD-001 — Anonymous sign-ins still mint authenticated profiles with 200 points

- **Severity:** Critical
- **Location:** `supabase/config.toml:179-182,206-208`; `supabase/migrations/20261108_auth_profiles.sql:41-61`; `tests/invariants/authorization.test.ts:304-335`
- **Description / root cause:** The local Supabase auth configuration still enables anonymous sign-ins (`enable_anonymous_sign_ins = true`) and permits 1,000 anonymous users per hour per IP. The auth trigger creates a profile for every auth user with 200 points and role `FAN`. Anonymous Supabase users therefore receive the `authenticated` database role and can execute every RPC granted to it, including `create_club`, `create_club_event`, `purchase_ticket`, `open_trade`, `claim_ticket` and `register_for_tournament`.
- **Evidence:** `README.md:43` and `175-176` state that there are no anonymous sessions. `docs/architecture/01-system-overview.md:64-65` says the same. ADR-009 §Decision says `Anonymous fan sign-in is removed`. The config comment still says `Local demo: fans sign in anonymously`. The authorization suite contains a test named `an anonymous fan is a real auth user and can trade on their own profile`; it asserts that an anonymous user receives a profile with 200 points, can call `open_trade`, and is only refused because that user is not an organizer. The test is evidence that the behaviour is real, not merely config drift.
- **Impact:** An unverified person can obtain a stable authenticated identity, create a club, issue tickets, trade with 200 starting points, claim tickets and register for events. Repeating the anonymous sign-in creates independent identities with fresh points, enabling sybil trading, market distortion, reward claims and capacity consumption. It also contradicts the cross-club email/password identity model and the README's security claim.
- **Remediation options:**
  1. Set `enable_anonymous_sign_ins = false`, replace the anonymous test with a refusal test, and verify that `create_club`, `open_trade`, `purchase_ticket` and `claim_ticket` reject a session without an email/password identity. This is the recommended option.
  2. Keep anonymous sessions only for a clearly scoped legacy path, with no points, no club creation and no trading, and document the exception. This preserves the v2 demo but keeps the identity model split.
- **Recommended action:** Disable anonymous sign-ins now and treat any existing anonymous profiles as local data that can be reset. Add a CI assertion that anonymous sign-in fails. Do not deploy this configuration to a hosted environment.
- **Verification required:** Auth configuration test; negative tests for each authenticated RPC with an anonymous session; a fresh database reset; a check that the authorization suite no longer needs `createAnonymousUser`.
- **Uncertainty / limitations:** The configuration is the observed local/CI configuration. A hosted Supabase project could have a different setting, but there is no hosted deployment and no separate production configuration in the repository. The finding is therefore confirmed for the only environment the repository defines.
- **Related issue / plan / PR:** Issue [#171](https://github.com/match-pulse/match-pulse/issues/171); related FND-001.

### AUD-002 — Former staff retain attendee identity through a legacy RLS policy

- **Severity:** Critical
- **Location:** `supabase/migrations/20261121_mvp_rls.sql:27-38`; `supabase/migrations/20261203_v3_club_rpcs.sql:678-685`; `supabase/migrations/20261202_v3_club_rls.sql:497-508`; `supabase/migrations/20261203_v3_club_rpcs.sql:597-631`
- **Description / root cause:** The v2 policy `tickets_select_organizer` grants `SELECT` on every ticket for a tournament whose `organizer_id` equals `auth.uid()`. The v3 `create_club_event` sets `organizer_id` to the staff member who created the event. The v3 migration adds `tickets_select_club_staff` but never drops the legacy policy, and `remove_club_member` deletes the membership row without clearing `organizer_id`. The policies are permissive and therefore OR'ed: current staff and the original creator can both read the full ticket row.
- **Evidence:** The ticket table contains `attendee_first_name`, `attendee_last_name`, `attendee_date_of_birth`, `attendee_place_of_birth`, `attendee_tax_code`, `attendee_document` and `fan_card_number` (`20261201_v3_club_tenancy.sql:251-264`). The attendee RPC `list_club_attendees` correctly checks the current club role, but a direct PostgREST `select` on `tickets` does not use that RPC; RLS decides. The v3 isolation test checks a different club and an analyst, not a removed creator. The threat model claims `no private table reads` for club identity; this policy is a private table read.
- **Impact:** A staff member or admin who created an event can be removed or demoted and still read the names, dates of birth, places of birth, tax codes/documents and fan-card numbers of every attendee. This is a privacy and insider-risk breach after offboarding, and it contradicts ADR-010's restriction of attendee identity to current `OWNER`, `ADMIN` and `STAFF` members.
- **Remediation options:**
  1. Drop `tickets_select_organizer` and rely on `tickets_select_own` plus `tickets_select_club_staff` (current membership). This is the recommended option; the organizer RPCs already use current role checks.
  2. Replace it with a policy that checks `has_club_role(t.club_id, ...)` and a separate immutable creator field that is never used for data access. Reassigning or clearing `organizer_id` on removal is an alternative but weaker because the field has legacy meaning.
- **Recommended action:** Remove the legacy policy in a corrective migration, add a regression test that removes a staff creator and verifies direct `select` returns no rows, and review `registrations_select_organizer` for the same pattern.
- **Verification required:** Database test with a staff-created event, ticket purchase, member removal, direct `tickets` select and direct `registrations` select; confirm current staff still see the rows and the removed creator does not.
- **Uncertainty / limitations:** The policy is deterministic SQL; no runtime execution was needed to establish the access path. The audit did not test a real offboarding flow in a running environment.
- **Related issue / plan / PR:** Issue [#171](https://github.com/match-pulse/match-pulse/issues/171); related FND-001 and FND-008.

### AUD-003 — Market lifecycle is not tied to the match result

- **Severity:** Critical
- **Location:** `supabase/migrations/20261112_idempotent_rpcs.sql:74-89,383-399`; `supabase/migrations/20261204_v3_ticketing_rpcs.sql:1197-1234`; `supabase/migrations/20261203_v3_club_rpcs.sql:893-901`; `src/app/club/events/[id]/page.tsx:353-378`; `src/components/MarketTrader.tsx:97-100`
- **Description / root cause:** `open_trade` and `close_trade` check only that the market is `OPEN` and that database time is at or after `kickoff_time`. They do not check the match status. `resolve_market` checks only that the market is `OPEN` and that the caller has the club or organizer role; it does not require the match to be `FINISHED`, does not compare the winner with `home_score`/`away_score`, and does not reject a resolution before kickoff. The club event page displays the resolve form whenever `market_status = 'OPEN'`, and the market trader page says "the market is open" while the entry form is visible.
- **Evidence:** The public match view exposes `home_score`, `away_score` and `status` (`20261202_v3_club_rls.sql:207-223`), and the event page renders the score (`src/app/events/[id]/page.tsx:83-85`). The market page sets `open = resolvedWinner === null && started` and does not inspect `match.status` (`src/app/market/[id]/page.tsx:145-148`). The UI text says entries are allowed while the match is live, but the code allows them until resolution.
- **Impact:** After the final whistle, the winning outcome is public. A fan can buy the winning shares at a price below 1 and receive 1 point per share at resolution, extracting points from the market. A club can also resolve before the match or choose a winner that does not match the recorded score, paying arbitrary holders. Both are core market-integrity and points-economy failures.
- **Remediation options:**
  1. Close entries when `matches.status = 'FINISHED'` (or at a defined full-time boundary), require `FINISHED` before resolution, and require the winner to match the final score; add an explicit audited override for exceptional cases. This is the recommended option.
  2. Keep manual resolution but document it as an operator override, require an audit reason, and disable entries as soon as the match is finished. This preserves operational flexibility but removes the arbitrage window.
  3. Formally accept the current rule (entries until resolution, arbitrary organizer winner) as a product decision. This is not recommended because it permits points creation and is not covered by an explicit risk acceptance.
- **Recommended action:** Treat this as a product/domain decision, not a silent code fix. If the human chooses option 1 or 2, implement it in a corrective migration and add lifecycle tests for `FINISHED` entries, pre-kickoff resolution and score/winner mismatch.
- **Verification required:** Tests for entry after `FINISHED`, resolution before `FINISHED`, resolution with a mismatched winner, and UI/DB agreement; a negative test that the public score cannot be used to buy a guaranteed payout.
- **Uncertainty / limitations:** M-INV1 defines the current window as opening at kickoff and ending at resolution. The audit is challenging that invariant as a design decision, not claiming the code contradicts its own documented rule. The human must decide whether the current rule is accepted, changed or replaced.
- **Related issue / plan / PR:** Issue [#171](https://github.com/match-pulse/match-pulse/issues/171).

### AUD-004 — `max_per_buyer` is not enforced across orders

- **Severity:** Major
- **Location:** `supabase/migrations/20261204_v3_ticketing_rpcs.sql:305-308,334-335,389-398`; `openspec/changes/add-club-tenancy-and-cli/specs/ticketing/spec.md:24-33`; `tests/integration/v3-club-tenancy.test.ts:221-226`
- **Description / root cause:** `purchase_ticket` reads `max_per_buyer` and compares it only with the quantity of the current attendee array. It never counts the buyer's existing tickets or orders for the same event. `ticket_orders` permits multiple orders per buyer, and `tickets` has no cumulative per-event constraint. A buyer can therefore submit 4 tickets, then 4 more, and repeat up to the allocation.
- **Evidence:** The ticket-type spec says "A buyer SHALL purchase one to four tickets per event" and "WHEN a buyer attempts to purchase a fifth ticket for the same event THEN the purchase is refused." ADR-010 says "cap a buyer at four tickets per match." The integration test named "is capped at four" submits five attendees in one call; it does not test a second order. The CLI test does the same. - **Impact:** The per-buyer cap is ineffective against a buyer who places multiple orders; a single buyer can exhaust allocation, and the documented fairness/scalping control is not delivered.
- **Remediation options:**

  2. Add a database constraint or a `ticket_purchase_totals` counter per buyer/event, maintained transactionally. This is more invasive but makes the rule harder to bypass.
- **Recommended action:** Implement option 1, define whether the cap is per event or per ticket type, and add sequential and concurrent tests: 4 then 1 must be refused; two concurrent 4-ticket orders must not both succeed beyond the cap.

- **Uncertainty / limitations:** The cap could be intended per order rather than per event, but the field name, ADR, spec scenario and T-INV4 all describe a per-event buyer cap. If the intent is per order, the UI label and documentation must change; that is a product decision.

### AUD-008 — Cohort suppression is applied at market level

### AUD-010 — Venue capacity is not enforced for ticket sales

- **Location:** `supabase/seed.sql:9-21`; `supabase/migrations/20261204_v3_ticketing_rpcs.sql:1209-1221`
- **Description / root cause:** The seed tournament `Summer Cup 2026` has neither `club_id` nor `organizer_id`. Its market is linked to a match in that tournament. The v3 `resolve_market` for a tournament-linked, non-club market requires `v_organizer_id = auth.uid()`; because `organizer_id` is null, every caller is distinct from it and is refused. A market without a tournament link would be open to any organizer, but this one is linked.
- **Evidence:** Seed insert at `supabase/seed.sql:9-21` (no organizer_id/club_id); resolve branch at `20261204_v3_ticketing_rpcs.sql:1213-1221`; the comment says the seeded market is the demo market.
- **Impact:** The seeded market can accumulate positions but never settle. The local demo cannot demonstrate resolution or payouts for that market; a user may think the market is stuck.
- **Remediation options:**
  1. Assign the seed tournament to a fixture organizer or club, or create the seed market under the demo club. This is the recommended option.
  2. Remove the seed market and rely on `auth:organizer` for the v3 demo.
- **Recommended action:** Fix the seed fixture and add a smoke assertion that the seeded market can be resolved by the fixture owner.
- **Verification required:** Seed, sign in as the fixture organizer, resolve the seeded market, assert payouts; a fresh `db reset` run.
- **Uncertainty / limitations:** The audit did not execute `supabase db reset`; the finding is based on the seed SQL and the resolve branch.
- **Related issue / plan / PR:** Issue [#171](https://github.com/match-pulse/match-pulse/issues/171).

### AUD-017 — Ticket purchase idempotency does not cover the payload

- **Severity:** Minor
- **Location:** `supabase/migrations/20261204_v3_ticketing_rpcs.sql:361-387`; `src/components/EventCheckout.tsx:16,44-46`; `src/cli/index.ts:73,258-266`; `docs/operations/failure-modes.md:22,28`
- **Description / root cause:** The ticket replay path checks the existing order's `ticket_type_id` and `quantity`, but not the attendee array, channel or buyer data. A retry with the same request ID and a different attendee payload returns the original order silently. The web checkout keeps one request ID for the component lifetime and resets it only after a successful purchase, not when the ticket type or attendee payload changes. The CLI generates a new request ID on every invocation and its usage line does not mention `--request-id`, so a retry after an ambiguous failure can create a second order.
- **Evidence:** Replay comparison at `:369-371`; the hidden request ID at `src/components/EventCheckout.tsx:16,33`; the CLI request ID at `src/cli/index.ts:264` and usage at `:73`. The failure-modes document says the key is reused on retry and rotated on payload change.
- **Impact:** A user who retries with changed attendee data can receive an order that does not match the submitted data, or a CLI retry can duplicate a purchase. The practical impact is limited by the short window and the max-per-order rule, but the retry contract is not met.
- **Remediation options:**
  1. Store a payload hash (type, quantity, attendee fields, channel, buyer) with the order and refuse a mismatch. Rotate the client key whenever the payload changes, and print/document the CLI key. This is the recommended option.
  2. Only treat the request as a replay when the full payload matches; otherwise raise a clear conflict.
- **Recommended action:** Implement option 1 or 2 and add tests for changed attendees and CLI retries.
- **Verification required:** Sequential replay with identical payload, changed attendee payload refusal, CLI retry with same/different key, and a test that no second order/ticket is created.
- **Uncertainty / limitations:** The audit did not execute the web or CLI flow.
- **Related issue / plan / PR:** Issue [#171](https://github.com/match-pulse/match-pulse/issues/171); related FND-003 and AUD-012.

### AUD-018 — Club-controlled point issuance is unbounded

- **Severity:** Informational
- **Location:** `supabase/migrations/20261203_v3_club_rpcs.sql:664-665`; `supabase/migrations/20261204_v3_ticketing_rpcs.sql:446-449`; `supabase/migrations/20261120_mvp_schema.sql:36-52`
- **Description / root cause:** `create_club_event` accepts any non-negative `ticket_points`, and `purchase_ticket` awards that value per ticket to the buyer. Points are global across clubs; rewards are club-scoped but their cost is paid in global points. There is no platform cap, approval, emission budget or audit of the total supply.
- **Evidence:** The validation is only `p_ticket_points < 0`; the award is `points + (v_ticket_points * v_quantity)`. The reward redemption only checks the balance. The product uses simulated points, but the rewards are a user-facing discount promise.
- **Impact:** A club can mint an arbitrarily large number of points, and a fan who buys a ticket at another club can then redeem that club's rewards. The economy has no defined supply or anti-inflation rule. The immediate impact is limited by simulated commerce and the requirement to hold a ticket for the reward club, but the design is not bounded.
- **Remediation options:**
  1. Define a platform cap or approval for `ticket_points`, and record the total issued. This is the recommended option if rewards are meaningful.
  2. Explicitly document points as a per-club simulated token and accept that clubs control issuance. This requires a product decision.
- **Recommended action:** Ask the human to decide whether point issuance is a platform or club control. Do not treat the current unbounded value as an approved economy.
- **Verification required:** Boundary test for the chosen cap; an audit/report of issued points; a reward redemption test across clubs.
- **Uncertainty / limitations:** This is a design observation, not a code defect against a documented invariant. The audit did not model the economy.
- **Related issue / plan / PR:** Issue [#171](https://github.com/match-pulse/match-pulse/issues/171).

### AUD-019 — Subscription period end is not enforced

- **Severity:** Informational
- **Location:** `supabase/migrations/20261201_v3_club_tenancy.sql:80-89`; `supabase/migrations/20261202_v3_club_rls.sql:69-101`; `supabase/migrations/20261203_v3_club_rpcs.sql:271-280`
- **Description / root cause:** `club_subscriptions.current_period_end` is set to `NOW() + 30 days` on creation and plan assignment, but `has_entitlement` and `entitlement_limit` check only `status = 'ACTIVE'`. No scheduled job or RPC expires an active subscription. An `ACTIVE` row with a past `current_period_end` continues to grant entitlements indefinitely.
- **Evidence:** The field and status are defined at `20261201:80-89`; the entitlement queries filter status only; `admin_assign_plan` resets the period end but nothing reads it. The README says commerce is simulated and there is no billing provider.
- **Impact:** The period end is decorative. If the product later treats subscriptions as time-bound, expired clubs would retain access until manually changed. In the current simulated demo, the impact is low, but the data model and behavior disagree.
- **Remediation options:**
  1. Define that subscriptions are manually managed and remove/ignore `current_period_end` in the entitlement decision, documenting the choice. This is the smallest option.
  2. Enforce expiry in `has_entitlement`/`entitlement_limit` and add a renewal/expiry process. This is the recommended option if period end is meaningful.
- **Recommended action:** Ask the human whether period end is a real rule. Align the schema, RPCs and documentation.
- **Verification required:** An expired active subscription is either denied or explicitly documented as manual; a test for the chosen rule.
- **Uncertainty / limitations:** No billing or scheduling exists, so this may be intentionally out of scope.
- **Related issue / plan / PR:** Issue [#171](https://github.com/match-pulse/match-pulse/issues/171); related AUD-011.

### AUD-020 — Plan limits are not concurrency-safe

- **Severity:** Minor
- **Location:** `supabase/migrations/20261203_v3_club_rpcs.sql:420-430,503-508,668-676`
- **Description / root cause:** `invite_club_member`, `accept_club_invite` and `create_club_event` each count current rows, compare the count with `entitlement_limit`, and then insert. None of them locks the club or subscription row that owns the limit. Concurrent transactions can all read the same count and all insert, exceeding `max_members` or `max_active_events`. The invite path locks no shared row; the accept path locks only the individual invite; the event path locks no club row.
- **Evidence:** The invite count/guard is at `:420-430`; the accept count/guard is at `:503-508`; the event count/guard is at `:668-676`. T-INV3 says plan limits are enforced. The v3 integration and CLI tests exercise only sequential active-plan limits; no concurrent limit test exists.
- **Impact:** A club can exceed its plan limits with parallel requests. The impact is bounded to member/event quotas rather than data corruption, but it weakens plan separation and the stated entitlement control.
- **Remediation options:**
  1. Lock the `club_subscriptions` or `clubs` row `FOR UPDATE` before the count/insert, so the limit check and insert serialize. This is the recommended option.
  2. Maintain a transactional counter with a database constraint, similar to the tournament capacity counter. This is more invasive but makes the limit unrepresentable.
- **Recommended action:** Implement option 1 for member invites/accepts and event creation, and add concurrent tests that fire more requests than the remaining limit.
- **Verification required:** Concurrent invite/accept/event-create tests; assert the final member/event count never exceeds the active plan limit and refusals leave no partial rows.
- **Uncertainty / limitations:** The race requires concurrent requests and was not executed in this environment. The count-then-insert pattern is visible in the SQL.
- **Related issue / plan / PR:** Issue [#171](https://github.com/match-pulse/match-pulse/issues/171); related AUD-011 and AUD-012.
